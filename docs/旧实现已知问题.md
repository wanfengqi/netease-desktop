## 一、必须按旧语义复刻（改了会变手感）

### 1.1 order 模式手动 next 在末尾会回绕，不自停
- **位置**：`player.js:87`，兜底 `(index + 1) % n`，只有 `auto=true` 才返回 -1
- **现象**：用户点"下一首"到最后一首会跳回第一首继续播；直觉上"顺序播放"应该停，实际不会
- **S1 处置**：【按旧语义复刻】已写测试锁死

### 1.2 one 模式手动 next 真的会走人
- **位置**：`player.js:79`，单曲循环只在 `a.onended`（auto=true）时重复
- **现象**：手动按下一首落到 `(index+1)%n`，歌就变了。原注释"单曲循环只在自动续播时生效"极易被误读成"手动也不走"
- **S1 处置**：【按旧语义复刻】

### 1.3 prev() 无条件先吃历史栈，与播放模式无关
- **位置**：`player.js:66-73`，**没有判断 `playMode === 'shuffle'`**
- **现象**：历史栈里有货就 pop —— 所以**列表循环模式下点上一首也可能跳到"上次从哪跳过来的"而非 index-1**
- **注意**：多数需求文档会写成"随机模式下优先走 shuffleStack"，**这是偏窄的描述**，真实行为是全模式优先
- **S1 处置**：把 `popHistory` 做成模式无关的独立函数，**"要不要用"留给调用方**
- **⚠️ S3 接线要求**：必须保持无条件优先，否则上一首手感会变

## 二、待修问题（必须修 + 必须带测试）

### 2.1 playAt 竞态无序号保护（最严重）
- **位置**：`player.js:121-164`，async 且无 requestId
- **现象**：快速连点切歌时多个 playAt 交错 await 取址，**先发的请求可能后返回，把已经切走的歌的 url 写进 audio 并播放** —— 表现为"点了 B 却在放 A"
- **旧代码的错误处置**：只用 `isPlayAbort` 掩盖随之而来的 AbortError 报错，**没解决错序本身**
- **S1 处置**：AudioEngine 是纯执行器（url 由调用方取），无法单方面修
- **S2 处置**：新增 `UrlResolver`（token 递增 + `isCurrent(token)`），调用方 await 回来比对，不匹配即丢弃。**必须带并发竞态测试**

### 2.2 clearQueue 不清理 shuffleStack
- **位置**：`player.js:220-223`，`removeAt` 也不碰历史栈
- **现象**：clearQueue 之后 shuffleStack 仍留旧索引；若之后 setQueue 到更长的列表，这些残留索引可能重新"有效"，被 prev() 弹出来播到莫名其妙的位置
- **S1 处置**：保留旧语义（测试锁成"removeAt 不清理历史栈"），同时让 `popHistory` 边界安全（丢弃过期索引）
- **⚠️ S3 要求**：clearQueue 时应一并清栈

### 2.3 shuffleStack 从不因删曲而清理
- **位置**：`player.js:203-218`，removeAt 不碰它
- **现象**：历史栈残留失效索引，靠 prev() 的 while + 边界校验静默丢弃 —— 用户感知是"上一首偶尔跳过头/连跳两层"
- **S1 处置**：把"脏数据 + 消费端兜底"契约显式建模为 `popHistory` 丢弃过期项，并写测试

### 2.4 MEDIA_ERR_SRC_NOT_SUPPORTED(4) 被误归因为 CORS
- **位置**：`player.js:682-691`，error code 4 且 eqReady 就拆链路 + 自动重播当前曲
- **现象**：code 4 的真实含义是"格式/地址不可用"，一律归因 CORS 会在**真的拿到坏 url** 时形成"拆均衡器→重播→还是 4→再拆"的循环，**每轮还上一次 toast**
- **S1 处置**：只暴露 `snapshot.errorCode` 与常量，判定留给 S2/S3
- **⚠️ S3 要求**：判定必须区分"真的坏 url"与"crossOrigin 残留"，且循环要有次数上限

### 2.5 两套落盘节流不对称
- **位置**：`player.js:229-238`（recordRecent 每次 playAt **立即** `config.set`，整个 200 条数组同步写盘） vs `player.js:258-262`（队列持久化 **800ms 防抖**）
- **现象**：快速切歌时 recents 写盘 N 次、queue 只写 1 次
- **⚠️ S3 要求**：接 config 时不要照搬，统一走防抖

### 2.6 restoreQueue 恢复 index 却不校验身份
- **位置**：`player.js:240-255`，直接用 queueIndex，只做 `index >= length → -1`
- **现象**：不验证该位置的歌是否还是当初那首（队列被截断到 300 条后顺序可能变）—— "上次听到第 5 首，重开变成第 5 个别的歌"
- **S1 处置**：`createQueue` 保持同样不校验语义，但提供 `currentKey()` 让 S3 可做"持久化连 key 一起存、恢复时校验"
- **⚠️ S3 要求**：持久化必须存 key，恢复时校验

## 三、技术陷阱（照做，别问为什么）

### 3.1 crossOrigin 三态陷阱
- **位置**：`player.js:436-455`
- **陷阱**：咪咕分支**同时**做 `removeAttribute('crossorigin')` **和** `a.crossOrigin = null`，**两个都必须做**
- **原因**：只赋 null 在部分 Chromium 版本不触发属性移除，残留的 `anonymous` 会让咪咕直接 `MEDIA_ERR_SRC_NOT_SUPPORTED` 哑音
- **S1 处置**：保留双保险，`defaultCrossOriginPolicy` 可注入
- **顺序铁律**：`crossOrigin` 必须在设 `src` **之前**设好
