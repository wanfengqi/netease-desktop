# S2 遗留问题与 S3 交接要求

> 来源：S2 阶段执行报告 + 协调者独立复验（2026-10-25）。
> 独立复验结论：135 测试自跑全绿、typecheck exit 0、`src/` 零改动、真实联网四路全通（网易云搜索 275 条 / 取址 319B / personalized 3 / toplist 65；咪咕搜索 20 条）。

---

## 一、必须由 S3 处理的问题

### 1.1 均衡器新旧字段并存（会有歧义）
- **现状**：旧 config 的 equalizer 是 `{on, preset, gains}`，新格式定义了 `{enabled, bands}`
- **S2 的处置**：原字段全保留 + 补新字段，两者并存
- **S3 必须做**：接均衡器时做一次 in-place 升级，不留两套
- **风险**：若不升，UI 读 `enabled` 与 `on` 会得到不同结论

### 1.2 主进程不再瘦身，超大响应直穿 IPC
- **现状**：瘦身下放到每个 repository 方法的 picker；网易云响应原样透传
- **实测风险**：`/toplist` 单次 74KB、`/playlist/detail` 可达 300-500KB
- **S3 要求**：若遇到 >1000 首的超大歌单，在 **transport 层**加"响应体积阈值 + 分页"，**不要**退回主进程加 if 分支（那会让主进程重新膨胀，违背 S2 的解耦目标）

### 1.3 部分接口拿不到数据（如实记录，不要伪造）
| 接口 | 实测结果 | 处置 |
|---|---|---|
| 咪咕 `getSimilarSongRecommend` | 服务端恒返回 `contents: []` | 已实现但无数据；S5 相似推荐改用网易云 `simi_song` |
| 咪咕 `getTodayRecommend` | 需 `pacmToken` 登录态，返回 200205 | 已实现并抛不可重试错误；S5 每日推荐改用网易云 `recommend_songs`（需 cookie） |
| 咪咕 `getNewSongList` | 返回导航壳（itemList 是 tab 的 actionUrl），无歌曲实体 | 只透出 `newSongTabs()`；新歌改用网易云 `personalized/newsong` |
| 网易云 `/recommend/songs` | 需 cookie，无 cookie 直接抛错 | 已单测覆盖，不消耗网络请求 |
| 网易云 `/song/url/v1` 部分歌曲 | `url: null`（实测 id=186016 晴天 code=404） | 不是 bug，接口如实返回；UI 需提示"无版权/VIP" |

### 1.4 咪咕字段名不一致的坑
- `searchAlbum` 的结果项是 `items[].dalbum`（**不是** `album`），字段是 `contentId/title/imgItems/publishDate`，与 `ZJ-Album-Item` 的 `resId/txt/txt3` 完全不同
- 已单独建模为 `MiguDAlbumRaw`，**调用方容易踩**
- `getAlbumSong` 传 `contentId` 或 `resId` **两种都返回 `songList: []`**
- **S3 待试**：改用 `getDAlbumSong` 看是否成功

## 二、旧版既有缺陷（S3 可一并修）

### 2.1 旧版日志泄漏 cookie 明文
- **位置**：`src/main.js` 把带 cookie 的完整 URL 打进 `[api]` 日志（`/login/status?...&cookie=MUSIC_A_T=...` 整串明文）
- **新版已修**：`electron/services/neteaseApi.cjs` 只记 path 与大小，**不记 query**
- **S3 建议**：一并修旧版这条日志（当前按边界未改 `src/`）

## 三、环境注意事项

### 3.1 残留进程会占 3300 端口
- **现象**：`release/win-unpacked/网易云音乐桌面版.exe` 残留进程会占 3300，导致 `npm start` 的 API 子进程退出 code=1
- **处置**：出现"旧版起不来"时，先查 `tasklist | grep 网易云` 与 3300 端口占用
- **端口规划（刻意错开）**：旧版 3300-3400，新版 3500-3600，两版可同时运行互不抢占

### 3.2 咪咕 SDK 导出数以实测为准
- 子代理报告称 110 个导出，**协调者实测为 124 个**
- 差异原因：统计口径（可能只数了函数，未含常量/其它导出）
- **以后引用一律以 `Object.keys(m).length` 实测为准**

## 四、S2 交付的可用能力清单（S3 可直接用）

### 4.1 渲染层 repository
- `app/src/data/repository/netease.ts` — 16 个方法，每个自带 picker
- `app/src/data/repository/migu.ts` — 15 个方法
- `app/src/data/repository/index.ts` — 出口 + 共享单例

### 4.2 基础设施
- `transport.ts` — TransportError / withTimeout / withRetry（指数退避）/ 双源业务码校验
- `urlResolver.ts` — **带 token 的取址协调器，修掉 S1 发现的"点 B 放 A"竞态**
- `config.ts` — 新配置类型

### 4.3 竞态修复的实测证据
```
fast { token:2, hasUrl:true,  isCurrent:true }
slow { token:1, hasUrl:false, isCurrent:false, error:"过期请求（已切歌）" }
```
S3 接线时**必须**让取址走 UrlResolver 的 token 校验，否则竞态会复活。
